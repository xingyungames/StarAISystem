# ⑦ 工具层

> 代码：`src/StarGameAI/Tools/`（`Tooling.cs` 准入、`BuiltinTools.cs` 内置工具）、`Core/Sandbox.cs`
> 配置：`config/tools.policy.json`
> 页面：后台 `#tools`（工具）、`#sandbox`（沙箱）

一句话：**让它能从"说"变成"做"，同时保证做了不该做的能被看出来。**

## 自生成工具的四道闸

`Tooling` 负责把 AI 自己写的脚本变成"可用工具"：

```
① 契约      脚本必须声明 name / description / 参数 schema
② 静态检查  禁用清单（不碰网络、不碰系统路径、不 import 危险模块）
③ 试跑      用样例参数跑一次，看退出码和输出
④ 自动准入  全部通过 → status=active，否则 pending 等人审
```

工具以 **Python 子进程**执行，环境变量白名单化（`tools.policy.json` 的 `env_allowlist`）。

## 调用与留痕

模型调工具走的是标准的 function calling：系统提示里列出所有 `active` 工具，
模型返回 tool_calls，服务端执行后把结果作为 tool 消息回填，再继续生成。

每次调用记一个 `tool` span（见 [可观测性](10-可观测性.md)），包含：
工具名、耗时、成功与否、入参长度、出参长度。**不记完整参数内容**。

---

## 一个曾经踩过的坑：假装调了工具

实盘出现过：模型回复"我已经写好了 xxx 文件"，**但根本没有产生 tool span**。

原因不是工具坏了，是模型直接编了一段"我做完了"的话。对策：

1. 系统提示里加硬规矩：**工具是真实动作，不是修辞**。要声称做过什么，必须真的调用
2. 工具调用与结果必须有 span 佐证
3. `NapcatActionAsync` 的成功判定放宽到 `status=="ok" || retcode in {0,200}`
   （NapCat 不同接口的成功码不一致，早期把 `retcode=200` 误判成失败）

## 在线状态会拦住动作

`qq_send_private` / `qq_poke` / `qq_send_file_*` 在目标被判定为**不可打扰**时会直接拒绝。

判定优先级：手动设定 > 用户自报（"我要睡了 / 在上课"）> 最近活动 > 静默时段 > 允许时段。

这就是"在线状态"这一层的实际用途——它不是给人看的仪表盘，是工具层的硬闸。

## 配置（`config/tools.policy.json`）

| 参数 | 作用 |
|---|---|
| `auto_approve` | 是否自动准入（关掉 = 每个新工具都要人工审） |
| `denied_modules` | 静态检查的禁用 import 清单 |
| `env_allowlist` | 子进程可见的环境变量 |
| `timeout_seconds` | 单次执行超时 |
| `max_output_bytes` | 输出截断 |

## 常见故障

| 现象 | 原因 |
|---|---|
| 说做了但没做 | 没产生 tool span。硬规矩 + 事后核对 |
| 工具调用失败但 `retcode=200` | 已修：成功判定接受 `ok` / `0` / `200` |
| `sb_write` 成功但没文件 | 沙箱路径被规范化后落到别处；看 trace 里的工具参数 |
| 工具不可用 | `status != active`，去「工具」页看准入卡在哪一道 |
