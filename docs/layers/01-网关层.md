# ① 网关层

> 代码：`src/StarGameAI/Gateway/`（`Receiver.cs` / `Sender.cs` / `OneBot.cs` / `Dedup.cs` / `NapcatHealth.cs`）
> 配置：`config/server.json`、`config/secrets.json`

一句话：**把 QQ 里发生的事，变成一条落盘的记录，再把要说的字送回去。**

---

## 入站：一条消息要过五关

```
NapCat HTTP 上报 POST /
  ① 鉴权      HMAC-SHA1 校验原始 body
  ② 去重      同 message_id 只处理一次
  ③ 拍平      OneBot 消息段数组 → 纯文本 + 占位符 + 真 @ 判定
  ④ 落盘      先写 data/log/<日期>/<scope>.jsonl，再谈别的
  ⑤ 入队      交给 InboundWorker 串行处理
```

### ① 鉴权：为什么不是 Bearer

NapCat 的 HTTP 上报**不发 `Authorization`**，带的是：

```
x-self-id:   10000
x-signature: sha1=<hex>    # hex = HMAC-SHA1(key = report.token, data = 原始 body 字节)
```

两个必须记住的点：

- **必须对原始字节做 HMAC**。先解码成字符串再编码会算错。
- **响应必须是空体 200**——NapCat 会把响应体当作"快速操作"继续解析。

另外保留 `Authorization: Bearer <report.token>` 作为手工 curl 的调试通道。

### ② 去重

按 `message_id` 记最近 N 条（容量与 TTL 在 `server.dedup`）。NapCat 在网络抖动时会重投。

### ③ 拍平：这是最容易丢信息的一步

OneBot 的消息是段数组：

```json
[{"type":"at","data":{"qq":"..."}}, {"type":"text","data":{"text":"你好"}}]
```

拍平之后变成 `@某人 你好`。关键产物有三个：

| 产物 | 用途 |
|---|---|
| `text` | 纯文本，后续一切判断都基于它 |
| `Segments`（briefs） | 保留了段类型，用来判断"这条里有图片吗" |
| **`Addressed`** | **只有当 `at` 段的 qq 等于 self_id 时才为真** |

`Addressed` 是协议层给出的、最可靠的一个信号——**比任何字符串匹配都准**。
所以「真 @ 了」和「正文里提到我的名字」被严格分开：

- 真 @ → 发言门直接判被动回复
- 名字在正文里 → 交给模型带着上下文判断

`[图片]` / `[表情]` / `[语音]` 这类占位符是拍平的副作用。它们最容易张冠李戴，
所以拼上下文时会显式标注归属（见 [记忆层](03-记忆层.md) 的上下文部分）。

### ④ 落盘先于一切

**日志在发言门之前写。** 这是有意为之：

- 审计日志要求全量、不可丢——包括被过滤、被判"不说话"、被白名单挡掉的
- 巩固阶段唯一的原料来源就是它
- 对话分块的观测也需要看到"没被回复的那些消息"

代价是：日志 ≠ 对话。它是一份流水账，不能直接当上下文用。
**这个区别是很多问题的根源**，见 [对话分块](06-对话分块.md)。

### ⑤ 入队：全局串行

`InboundWorker` 用**一个全局信号量**串行处理。不是按 scope 并行，是全部串行。

原因：会话状态（冷却、额度、在线状态）是共享的，并行会打架。
代价：一条消息的延迟会影响下一条——这也是"答的时机不对"的一部分成因。

## 出站：分段与追加

`Sender` 负责把生成的一段文本变成实际的 QQ 消息：

| 能力 | 说明 |
|---|---|
| 分段发送 | 模型用 `\n\n` 换段，按空行切成多条发出去，条数上限 `ratelimit.reply_max_segments` |
| 延迟 | 段之间按 `idea.burst.segment_delay_ms` 留间隔，不刷屏 |
| 发送审计 | 每次发送记 `data/audit/send.jsonl` |
| 在线状态拦截 | 目标被判定为"不可打扰"时，`qq_send_private` 等工具会被拒 |

**追加机制**（`ChatPipeline.TryBurstAsync`）：主回复发完后，按权重决定要不要再补几句。

| 约束 | 值 |
|---|---|
| 一次连贯发言上限 | `burst.max_messages`（默认 10，含已发出的） |
| 继续追加概率 | `base_probability × decay^k`（默认 0.7 × 0.6^k，水位越走越低） |
| 只在 `can_stop=true` 边界允许停 | 模型每条自带该标记 |

最后一条由服务端强制置 `can_stop=true`；若权重不够继续但话没说完，会额外请求一句收尾，
避免"说一半因为权重停了"的断层。

## 健康检查

`NapcatHealth` 每 15 秒探一次 NapCat 的 API，结果进后台「服务器」页与仪表盘。
NapCat 掉线时网关仍然收不到消息，但后台能立刻看出来。

## 关键参数（`config/server.json`）

| 参数 | 作用 |
|---|---|
| `listen.port` | 本服务监听端口（默认 11221） |
| `napcat.api_base` | NapCat OneBot HTTP 地址 |
| `self_id` | 机器人 QQ，用来跳过自己发的消息、判定真 @ |
| `whitelist.groups` / `private` | 白名单，两个都空 = 不设限 |
| `dedup.capacity` / `ttl_minutes` | 去重窗口 |
| `ratelimit.*` | 每秒/每分/每天限额、单条字数、分段数 |
| `context.max_history_messages` / `max_context_chars` | 历史注入预算 |

## 常见故障

| 现象 | 原因 |
|---|---|
| 401 | 签名算错（最常见：对字符串而不是原始字节做 HMAC） |
| NapCat 收到异常 | 响应体不是空的 |
| 消息全丢 | `self_id` 配错，自己的消息没被跳过；或白名单把来源挡了 |
| 重复回复 | 去重窗口太短 / 重启后内存去重表清空 |
| 发消息 403 `token verify failed` | `secrets.json` 里 NapCat token 的键名或值不对 |
